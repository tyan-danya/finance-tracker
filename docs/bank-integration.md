## 1. Краткое резюме и вердикт

Коротко, если читать нечего кроме этого раздела:

- **Прямого легального доступа к счёту физлица у стороннего Android-приложения в РФ, как
  правило, нет.** Банковские API ориентированы на юрлиц/ИП (эквайринг, расчётный счёт) либо
  требуют партнёрского договора и лицензионных условий, которые независимое приложение
  выполнить не может. Рассчитывать на «подключить Т-Банк по OAuth за вечер» — нельзя.
- **Единственный способ, работающий гарантированно и без юридических рисков, — импорт файла
  выписки, которую пользователь сам скачал в своём интернет-банке.** Это и есть Фаза 1.
- **Парсинг push-уведомлений** — реалистичный второй шаг: даёт «почти реальное время», но
  хрупок (банки меняют тексты) и требует аккуратной работы с политикой Google Play.
  Обязателен режим «не уверен → черновик на подтверждение».
- **Парсинг SMS** практически закрывает дорогу в Google Play. Возможен только как отдельная
  сборка для сайдлоада. Приоритет — низкий.
- **QR кассового чека / ФНС** — не замена выписке, а **обогащение**: детализация покупки по
  позициям. Интересно, но это отдельная фича, а не источник трат.

**Рекомендуемый порядок работ:** импорт выписки → парсер уведомлений → (если появится
юридическая возможность) API/агрегаторы.

## 2. Контекст: что уже есть в приложении

Чтобы оценки трудоёмкости были осмысленными, зафиксируем текущее состояние (см. `CONTRACT.md`):

- Хранилище — **Room**, `AppDatabase` версии **1**, `exportSchema = true`, миграций пока нет.
- Таблицы: `categories`, `subcategories`, `expenses`.
- `ExpenseEntity`: `id`, `amountMinor` (**копейки, `Long`**), `currency`, `categoryId`,
  `subcategoryId`, `epochDay`, `note`, `paymentMethod` (строка из `PaymentMethod`), `createdAt`.
- Все суммы — в минорных единицах; `Double` для денег запрещён. Любой импортёр обязан
  парсить `1 234,56` → `123456L`, а не через `Double`.
- Дата траты — **день без времени** (`epochDay`). В банковских данных есть **время** операции,
  и оно нужно для дедупликации → появится отдельное поле (см. §11).
- Категорий по умолчанию — 17 с подкатегориями (Продукты, Кафе и рестораны, Транспорт, Жильё,
  Здоровье, Одежда и обувь, Развлечения, Подписки и сервисы, Спорт, Образование,
  Красота и уход, Путешествия, Дети, Питомцы, Подарки, Финансы, Прочее). Это готовая целевая
  таксономия для автокатегоризации.
- Приложение **полностью офлайн**: нет сетевых зависимостей, нет аккаунтов, нет бэкенда.
  Любая интеграция, требующая сервера, — это качественный скачок в сложности и в
  ответственности за персональные данные.
- Из зависимостей доступны только те, что перечислены в `CONTRACT.md` (Compose, Room,
  kotlinx-serialization, coroutines). **Парсер XLSX/PDF потребует новых зависимостей** —
  это отдельное решение, которое нужно согласовать (см. §3.4).

## 3. Способ 1. Ручной импорт выписки (файл)

**Суть.** Пользователь заходит в свой интернет-банк или мобильный банк, выгружает выписку за
период, «расшаривает» файл в «Траты» (или выбирает через системный файловый пикер), видит
предпросмотр разобранных операций, правит категории и подтверждает импорт.

Это **самый реалистичный первый шаг**, поэтому разбираем его подробнее остальных.

### 3.1. Как это работает технически

Поток данных:

```
Файл (SAF / ACTION_SEND)
   → определение формата (по расширению + сигнатуре содержимого)
   → определение кодировки (BOM → эвристика UTF-8 → cp1251)
   → определение диалекта CSV (разделитель, кавычки)
   → сопоставление колонок с полями (профиль банка или ручной маппинг)
   → нормализация (сумма → копейки, дата → LocalDate, знак, валюта)
   → фильтрация (только расходы; исключить переводы себе)
   → автокатегоризация (§12)
   → дедупликация против уже существующих трат (§13)
   → экран предпросмотра: список строк со статусами
   → подтверждение → запись в БД одной транзакцией + запись в import_batches
```

Технически на Android нужно:

- **Приём файла.** `Intent.ACTION_OPEN_DOCUMENT` (Storage Access Framework) + обработка
  `ACTION_SEND` / `ACTION_VIEW` в манифесте, чтобы «Траты» появлялись в списке «Поделиться»
  из мобильного банка. Никаких разрешений на файловую систему не требуется — SAF даёт URI.
- **Чтение потока** через `ContentResolver.openInputStream`.
- **Работа в фоне** (`Dispatchers.IO`, корутина в ViewModel). Выписка на 5 000 строк —
  это секунды, но парсинг PDF может быть медленнее.
- **Предпросмотр и откат.** Импорт пишется одним батчем с общим `importBatchId`, чтобы
  пользователь мог одной кнопкой «Отменить импорт» удалить всё, что пришло этим файлом.

### 3.2. Форматы: что реально отдают банки

| Формат | Насколько распространён | Сложность парсинга | Комментарий |
|---|---|---|---|
| **CSV** | Высокая (веб-версии банков) | Низкая | Основной целевой формат Фазы 1 |
| **XLSX** | Высокая | Средняя | Нужна библиотека, новая зависимость |
| **PDF** | Очень высокая (часто единственный вариант в мобильном приложении) | Высокая | Табличный layout, нестабилен между версиями |
| **OFX / QIF** | **Практически отсутствует в РФ** | Низкая | Стандарты западного рынка; поддерживать «на всякий случай» смысла мало |
| **1C / txt (обмен с 1С)** | Только для бизнес-счетов | Средняя | Для физлица нерелевантно |

Отдельно про **OFX/QIF**: это хорошо специфицированные форматы, и парсер к ним пишется
быстро, но российские розничные банки их, насколько известно, не выгружают **[требует
проверки]**. Реализовывать имеет смысл только если найдётся конкретный банк-источник или
если появится задача мигрировать данные из другого приложения учёта финансов
(вот там OFX/QIF встречаются чаще).

### 3.3. Т-Банк (Тинькофф) — что ожидать

**[Все детали ниже требуют проверки на актуальной выгрузке — банк меняет формат.]**

По наблюдениям, веб-версия личного кабинета отдаёт **CSV** и **PDF**, мобильное приложение —
преимущественно **PDF** (и «поделиться» справкой об операциях).

Характерные свойства CSV-выгрузки Т-Банка, к которым надо быть готовым:

- **Кодировка `windows-1251`**, не UTF-8. Без BOM. Если открыть как UTF-8 — получим «крякозябры».
- **Разделитель `;`** (точка с запятой), потому что запятая занята под десятичный разделитель.
- **Десятичный разделитель — запятая**: `-1 234,56`. Плюс возможен **неразрывный пробел**
  (` `) как разделитель тысяч. Обязательно нормализовать все виды пробелов.
- **Расход — отрицательное число**, поступление — положительное.
- **Дата с временем**, формат вида `dd.MM.yyyy HH:mm:ss`.
- Обычно есть **две даты**: дата операции и дата списания/платежа. Они могут отличаться на
  1–3 дня (особенно у операций по карте). **Для учёта трат брать дату операции** — она
  соответствует моменту покупки, что ближе к смыслу поля «дата покупки» в приложении.
- Есть колонка **«Статус»**: `OK` / `FAILED` / ожидание. **Неуспешные операции импортировать
  нельзя.** Операции «в обработке» (holds) — либо пропускать, либо помечать как `PENDING`.
- Есть **сумма операции** и **сумма платежа** в разных валютах (при покупке за рубежом).
  Для рублёвого учёта брать сумму платежа в валюте счёта; исходную валюту сохранять в `rawText`
  или отдельном поле.
- Есть **MCC-код** — очень ценно для автокатегоризации (§12), надёжнее текста мерчанта.
- Есть **собственная категория банка** («Супермаркеты», «Транспорт», ...). Полезна как
  подсказка, но **не совпадает** с таксономией приложения — нужен маппинг.
- Есть **кэшбэк/бонусы** — это **не расход**, в траты не превращать.
- Есть колонки, специфичные для банка (округление на «Инвесткопилку» и т.п.), которые легко
  ошибочно принять за сумму.

**PDF-выписка Т-Банка** — форматированный документ со «шапкой» (ФИО, счёт, период) и таблицей.
Парсить можно, но это заметно дороже и ломается при редизайне.

### 3.4. Сбербанк — что ожидать

**[Требует проверки.]**

- В мобильном приложении выписка традиционно выгружается в **PDF** (часто ещё и защищённом
  паролем / с водяными знаками), в веб-версии бывает **Excel/CSV**. Конкретный набор форматов
  нужно проверять на живом аккаунте перед реализацией.
- В PDF-выписке назначение платежа часто **переносится на несколько строк** и при наивном
  извлечении текста склеивается с соседними полями. Это главная боль.
- Формат суммы: `1 234,56 ₽` — с символом валюты **внутри ячейки**, его нужно вырезать.
- Могут быть строки-разделители по датам («12 марта 2025») вместо колонки с датой в каждой
  строке — тогда дату нужно «протаскивать» сверху вниз.
- Категории банка могут присутствовать в PDF как отдельная колонка/подпись.

**Вывод по Сбербанку:** если у пользователя только PDF, качественный парсинг «из коробки»
не гарантирован. Честный план — сначала CSV/XLSX, PDF — отдельной итерацией и с явным
предупреждением «формат может распознаться не полностью, проверьте предпросмотр».

### 3.5. Типичные проблемы и как их решать

| Проблема | Проявление | Решение |
|---|---|---|
| **Кодировка** | Кириллица в «кракозябрах» | Определять: BOM → попытка строгого UTF-8 декодирования → fallback `windows-1251`. Дать пользователю ручной переключатель кодировки в предпросмотре |
| **Разделитель CSV** | Всё в одной колонке | Автоопределение по частоте `;`, `,`, `\t` в первых строках; учитывать кавычки |
| **Формат даты** | `12.03.2025`, `2025-03-12`, `12/03/25`, `12 марта 2025` | Список форматтеров, пробовать по очереди; при неоднозначности `dd/MM` vs `MM/dd` — приоритет русскому `dd.MM`, показать пользователю пример разбора |
| **Две даты** | Расхождение до нескольких дней | По умолчанию — дата операции; переключатель в настройках импорта |
| **Формат суммы** | `-1 234,56`, `1 234.56`, `1234,56 ₽`, неразрывные пробелы, `(123,45)` как минус | Нормализация: убрать всё, кроме цифр/минуса/разделителя; **парсить в `Long` копейки посимвольно**, не через `Double` |
| **Знак операции** | Расход то с минусом, то в отдельной колонке «Дебет/Кредит» | Профиль банка задаёт правило определения знака; в предпросмотре показывать «доходы будут пропущены: N шт.» |
| **Склеенное назначение платежа** | `Перевод по СБП Иванов И.И. Тел +7... Сообщение: за обед` | Не пытаться «понять» — класть весь текст в `rawText`, а в `note` — очищенную короткую версию (обрезать номера телефонов/карт, служебные префиксы) |
| **Мультистрочные ячейки** | Одна операция разбита на 2–4 строки файла | Склейка строк: строка без даты и без суммы — продолжение предыдущей |
| **Дубли внутри файла** | Одна операция дважды (перевыгрузка, пересекающиеся периоды) | Хеш строки + правила §13 |
| **Дубли между импортами** | Импортировали март, потом «январь–апрель» | `externalId` + окно дедупликации (§13) |
| **Переводы между своими счетами** | «Перевод на свой счёт», «Пополнение вклада» — это **не трата** | Эвристики: тип операции, ключевые слова, и главное — **парная операция** (в один момент времени равные суммы с противоположным знаком) → пометить обе как перевод и по умолчанию исключить |
| **Снятие наличных** | Формально расход со счёта, но деньги не потрачены | По умолчанию импортировать в «Прочее → Наличные снятие» либо предложить пользователю выбор политики |
| **Возвраты/отмены** | Отрицательный расход | Импортировать как корректирующую операцию либо пропустить с пометкой; в v1 модели данных **отрицательных сумм нет** — значит, пропускать и показывать в отчёте об импорте |
| **Комиссии** | Отдельные микрооперации | Импортировать в «Финансы → Комиссии банка» |
| **Валюта** | Покупки в USD/EUR | Пока модель однвалютная де-факто (`currency` есть, но UI рублёвый). Импортировать сумму **в валюте счёта**; исходную валюту и сумму сохранять в `rawText` до появления мультивалютности (см. `roadmap.md`) |
| **Огромные файлы** | Выписка за 5 лет | Потоковый парсинг, вставка батчами, прогресс-индикатор |

### 3.6. Что показывать пользователю (UX импорта)

Обязательный экран предпросмотра — это половина ценности фичи:

1. Шапка: «Найдено 342 операции, из них расходов 298, доходов 31, переводов между своими
   счетами 13, дублей 27, не распознано 4».
2. Список с чекбоксами и предложенной категорией у каждой строки.
3. Массовые действия: «снять все дубли», «назначить категорию выбранным».
4. Кнопка «Импортировать N операций».
5. После импорта — плашка «Импортировано. Отменить» (удаление по `importBatchId`).

### 3.7. Оценка и вердикт

| Параметр | Оценка |
|---|---|
| Юридические риски | **Нет.** Пользователь сам выгружает свои данные, приложение читает локальный файл |
| Надёжность | Высокая для CSV/XLSX, средняя для PDF |
| Работает офлайн | Да |
| Трудоёмкость (CSV + предпросмотр + дедуп + профили 2 банков) | **~4–7 дней** разработки |
| + XLSX | +1–2 дня и **новая зависимость** |
| + PDF (Т-Банк и Сбер) | **+5–10 дней**, и всё равно без гарантий |
| + миграция БД и модель данных | +1–2 дня (см. §11) |

**Вердикт: РЕКОМЕНДУЕМ. Это Фаза 1.** Начинать с CSV, XLSX — сразу следом, PDF — только
если по факту выяснится, что пользователи не могут получить CSV.

## 4. Способ 2. Открытые и партнёрские API банков

**Суть.** Приложение по OAuth получает от пользователя согласие и читает операции по его
счёту напрямую из API банка. Именно так работает открытый банкинг в ЕС (PSD2) и
UK Open Banking.

### 4.1. Честное положение дел в РФ

**[Раздел особенно чувствителен к устареванию — обязательно перепроверить перед реализацией.]**

- **Т-Банк.** Публичные программы API у банка исторически ориентированы на **бизнес**:
  эквайринг, приём платежей, работа с расчётным счётом ИП/юрлица, партнёрские сценарии.
  Доступа «стороннее приложение читает операции по карте физлица» в открытом
  самообслуживаемом виде, насколько известно, **нет**. Партнёрские интеграции существуют, но
  предполагают договор, юрлицо-партнёра и прохождение проверок банка. **[требует проверки]**
- **Сбербанк.** «СберБизнес API» — тоже про юрлиц и ИП (счета компании, выписки по
  расчётному счёту, зарплатные проекты). Плюс существуют продукты вида «Сбер ID»
  (авторизация) и эквайринг, но авторизация ≠ доступ к истории операций. **[требует проверки]**
- **Банк России / «Открытые API».** Регулятор ведёт работу по стандартизации открытых API
  (методические рекомендации и стандарты по обмену данными, в т.ч. по счетам физлиц), и есть
  направление на постепенный переход от добровольного применения к обязательному для крупных
  участников. **Конкретные сроки, перечень обязательных API и — главное — порядок допуска
  сторонних поставщиков услуг (аналог TPP/AISP в PSD2) нужно уточнять на момент реализации.**
  Скорее всего допуск будет требовать регистрации организации, а не «зарегистрировал
  приложение — получил токен». **[требует проверки]**

### 4.2. Почему это, как правило, недоступно приложению физлица

1. **Субъект договора — организация, а не разработчик-энтузиаст.** Партнёрский доступ
   оформляется на юрлицо, с проверкой, договором и, часто, требованиями к инфраструктуре.
2. **Требования к безопасности.** Взаимный TLS, сертификаты, аудит, хранение токенов —
   обычно подразумевается серверная часть. Мобильное приложение не может безопасно хранить
   `client_secret`: всё, что зашито в APK, считается публичным.
3. **Redirect-based OAuth требует зарегистрированного redirect URI** и, как правило,
   контролируемого домена — снова серверная часть.
4. **Экономика.** Партнёрские API часто платные или предполагают встречные обязательства
   (продажа продуктов банка), что несовместимо с бесплатным личным трекером.
5. **Ответственность за ПДн.** Как только появляется сервер, приложение перестаёт быть
   «данные не покидают устройство» и попадает под требования 152-ФЗ.

### 4.3. Оценка и вердикт

| Параметр | Оценка |
|---|---|
| Юридические риски | **Блокирующие** без партнёрского договора |
| Надёжность (если доступ есть) | Очень высокая — это единственный «настоящий» источник |
| Работает офлайн | Нет, нужен сервер |
| Трудоёмкость | **Недели–месяцы**, из которых бóльшая часть — не код, а договор и комплаенс |

**Вердикт: НЕ РЕКОМЕНДУЕМ на текущем этапе.** Оставляем как Фазу 3 «если появится
юридическая возможность». Действие сейчас: **раз в полгода проверять статус** открытых API
Банка России и наличие публичных программ доступа для приложений персональных финансов.

**Категорически не делать:** не пытаться использовать внутренние (недокументированные) API
мобильных приложений банков. Это нарушение условий использования, техническая мина
(ломается без предупреждения) и прямой путь к блокировке аккаунта пользователя.

## 5. Способ 3. Агрегаторы и провайдеры банковских данных

**Суть.** Между приложением и банками стоит посредник: у него есть договоры/интеграции с
банками (или собственные механизмы сбора), он отдаёт нормализованные операции и часто
готовую категоризацию по единому API.

На западном рынке это устоявшаяся модель (провайдеры агрегации счетов и категоризации
транзакций). В РФ такие сервисы тоже существуют, но чаще в B2B-виде — для банков и финтеха,
а не для независимых мобильных приложений. **Конкретный список доступных провайдеров,
их условия и наличие «розничного» тарифа — [требует проверки] на момент реализации.**

### 5.1. Плюсы

- Одна интеграция вместо N интеграций с банками.
- Нормализованная модель данных и, как правило, готовая категоризация «из коробки» — можно
  сильно сэкономить на §12.
- Провайдер берёт на себя поддержку изменений на стороне банков.

### 5.2. Минусы и риски

- **Персональные данные уходят третьей стороне.** Это полностью ломает главное обещание
  приложения — «ваши деньги видите только вы». Потребуется явное, отдельное, отзываемое
  согласие пользователя и честное описание, что именно передаётся.
- **Стоимость.** Обычно оплата за подключённый счёт/пользователя в месяц. Для бесплатного
  приложения это означает подписку — то есть другую бизнес-модель.
- **Требуется серверная часть** (ключи API нельзя держать в APK) → см. те же проблемы, что в §4.
- **Юрлицо и договор** — почти наверняка.
- **Зависимость от чужого качества.** Пропала интеграция с банком у провайдера — сломалась
  фича у нас, а объясняться перед пользователем нам.
- Часть провайдеров под капотом делает то самое скрейпинг-подключение по учётным данным
  пользователя — см. §15, такую модель мы не примем даже через посредника.

### 5.3. Оценка и вердикт

| Параметр | Оценка |
|---|---|
| Юридические риски | Высокие (ПДн, договор, согласия) |
| Надёжность | Средне-высокая, но вне нашего контроля |
| Работает офлайн | Нет |
| Трудоёмкость | Недели (интеграция) + сервер + договор + бизнес-модель |

**Вердикт: УСЛОВНО, не сейчас.** Рассматривать только если проект перестанет быть
локальным офлайн-приложением и появится подписка. Идея «данные не покидают устройство»
для нас пока важнее.

## 6. Способ 4. Парсинг SMS от банков

**Суть.** Приложение читает входящие SMS с коротких номеров банков и вытаскивает из них
сумму, мерчанта и остаток.

### 6.1. Как работает технически

- Разрешения: `READ_SMS` (чтение истории) и/или `RECEIVE_SMS` (broadcast на входящее).
- `BroadcastReceiver` на `SMS_RECEIVED` + разбор `SmsMessage`, либо запрос к
  `content://sms/inbox` для первичного импорта истории.
- Фильтрация по отправителю (алфавитные адреса банков) и набор regex-правил на каждый банк.

Типичный текст банковского SMS содержит: маску карты, тип операции (покупка/оплата/перевод),
сумму с валютой, мерчанта, время и остаток. Форматы у каждого банка свои и меняются.

### 6.2. Главная проблема — Google Play

Google Play ограничивает доступ к `READ_SMS` / `RECEIVE_SMS` / `READ_CALL_LOG`: их можно
использовать, только если приложение зарегистрировано в **одной из разрешённых Google ролей**
(классически — приложение по умолчанию для SMS/звонков) либо получило **явное исключение**
через декларацию в Play Console, где нужно доказать, что разрешение критично для основной
функции и нет альтернативы.

Ключевой момент: **у нас альтернатива есть — уведомления (§7) и импорт выписки (§3)**, и
именно на это ревьюер укажет. Приложения учёта финансов исторически получали отказы.
**Точный актуальный перечень разрешённых сценариев и процедура декларации — [требует проверки]
в Play Console на момент подачи.**

### 6.3. Что это значит для распространения

- Реалистичный исход: **приложение с `READ_SMS` не пройдёт в Google Play** или будет снято
  при очередной проверке политик.
- Значит, вариант существует только как:
  - отдельная **сборка для сайдлоада** (APK с сайта / GitHub Releases / F-Droid-подобная
    дистрибуция), либо
  - **build flavor** `sideload` с этой функцией, при том что в `play`-flavor разрешение
    вообще отсутствует в манифесте (иначе автоматика Play всё равно его увидит).
- Дополнительно: SMS-уведомления у многих банков давно отключены или платные — пользователи
  сидят на push. То есть фича ещё и теряет актуальность.

### 6.4. Риски

- Снятие приложения из стора, страйк на аккаунт разработчика.
- SMS — крайне чувствительные данные (там же одноразовые коды). Приложение с доступом к SMS
  автоматически становится привлекательной мишенью и требует куда более серьёзного отношения
  к безопасности.
- Репутационный риск: «зачем трекеру трат мои SMS» — законный вопрос пользователя.

### 6.5. Оценка и вердикт

| Параметр | Оценка |
|---|---|
| Юридические/сторовые риски | **Очень высокие** |
| Надёжность парсинга | Средняя (тексты меняются) |
| Актуальность источника | Падает (SMS вытесняются push) |
| Трудоёмкость | 3–5 дней на движок + по 0.5–1 дню на банк |

**Вердикт: НЕ РЕКОМЕНДУЕМ.** Если очень нужно — только в отдельном flavor для сайдлоада,
и **после** того, как заработает §7. Движок правил при этом общий с уведомлениями.

## 7. Способ 5. Парсинг push-уведомлений (`NotificationListenerService`)

**Суть.** Пользователь вручную выдаёт приложению доступ к уведомлениям; приложение слушает
уведомления от приложений банков и разбирает их текст в черновики трат.

### 7.1. Как это работает

- Сервис — наследник `NotificationListenerService`, объявленный в манифесте с
  `BIND_NOTIFICATION_LISTENER_SERVICE`.
- Разрешение **нельзя запросить диалогом**: пользователя нужно отправить в системные
  настройки («Доступ к уведомлениям») и он включает переключатель сам. Это надо честно
  объяснить экраном-онбордингом.
- В `onNotificationPosted` доступны: `packageName` (по нему фильтруем только банки),
  `extras` — `EXTRA_TITLE`, `EXTRA_TEXT`, `EXTRA_BIG_TEXT`, `EXTRA_SUB_TEXT`, время `postTime`.
- Работать нужно быстро и на фоновом диспетчере; результат — запись в очередь/БД.

### 7.2. Что можно вытащить

Из типичного банковского пуша реально извлекаются: сумма, валюта, тип операции
(покупка / оплата / перевод / зачисление / отмена), мерчант или получатель, маска карты/счёта,
иногда остаток. Времени операции в тексте часто нет — берём `postTime` уведомления.

Чего **нельзя**: MCC-кода, полного назначения платежа, идентификатора операции банка.
Поэтому уведомления дают «быстро и приблизительно», а выписка — «точно и полно».
Это ещё один аргумент за то, чтобы оба источника уживались (см. §13).

### 7.3. Стабильность

Главная слабость — **банк в любой момент меняет текст пуша**, и regex перестаёт совпадать.
Проектировать нужно исходя из того, что правила будут ломаться регулярно.

Принципы устойчивого дизайна парсеров:

1. **Набор правил на банк, а не один регэксп.** Правило = `{ packageName, приоритет, regex,
   именованные группы, тип операции }`. Правила пробуются по приоритету; первое совпавшее с
   валидным результатом — победитель.
2. **Именованные группы** (`amount`, `currency`, `merchant`, `card`, `kind`) — чтобы правило
   было декларативным и его можно было хранить в БД строкой, а не в коде.
3. **Правила лежат в БД (`parser_rules`), а не в исходниках.** Тогда обновление правил не
   требует релиза: базовый набор поставляется в assets как JSON и накатывается при апдейте,
   но пользователь/разработчик может добавить своё.
4. **Версионирование.** У набора правил есть `rulesVersion`; у каждой распознанной операции
   сохраняется `parserRuleId` и `rulesVersion` — чтобы понимать, каким правилом создана
   запись, и уметь переразобрать «сырой» текст новыми правилами.
5. **Всегда хранить `rawText`.** Если правило было плохое, из сохранённого сырого текста
   можно переразобрать позже. Без `rawText` фича невосстановима.
6. **Fallback обязателен:** не распознано → **не молча выбросить**, а создать запись со
   `status = UNPARSED` и показать в разделе «Требует подтверждения» с сырым текстом и формой
   быстрого ручного ввода. Пользователь ничего не теряет.
7. **Ничего не пишем в подтверждённые траты автоматически.** Даже успешно распознанное
   уведомление создаётся со `status = PENDING`, пока пользователь не подтвердит (или пока он
   явно не включит настройку «доверять распознанным операциям»).
8. **Уведомления-не-операции.** Реклама, «пришла зарплата», «доступен новый кредит»,
   напоминания — должны отсеиваться. Явные правила-исключения (blacklist) с приоритетом выше
   основных.
9. **Дедупликация внутри самих уведомлений.** Один и тот же пуш может прийти дважды/обновиться
   (`onNotificationPosted` вызывается и при апдейте). Ключ: `packageName + текст + округлённое
   время`.
10. **Тестируемость.** Движок правил должен быть чистой функцией
    `(packageName, title, text, time) -> ParsedOperation?` — тогда его покрывают юнит-тестами
    на корпусе реальных текстов, без Android.

### 7.4. Google Play и приватность

- Доступ к уведомлениям Play **разрешает**, но относится к нему строже, чем к обычным
  разрешениям: требуется, чтобы это была заявленная основная функция, с понятным раскрытием
  для пользователя (prominent disclosure) и отражением в политике конфиденциальности.
  Есть также требования раздела Data Safety. **Актуальные формулировки — [требует проверки].**
- Практика показывает, что финтех-приложения с парсингом уведомлений в сторе существуют —
  то есть путь проходимый, в отличие от SMS.
- Обязательно: экран с честным объяснением до запроса, возможность отключить,
  и **фильтр строго по списку package'ей банков** — не слушать всё подряд.

### 7.5. Оценка и вердикт

| Параметр | Оценка |
|---|---|
| Юридические/сторовые риски | Средние (проходимо при корректном раскрытии) |
| Надёжность | Средняя, деградирует со временем без поддержки правил |
| Работает офлайн | Да |
| Полнота данных | Низкая (нет MCC, нет ID операции) |
| Трудоёмкость (движок + UI подтверждения + правила на 2–3 банка) | **~5–8 дней** |
| Поддержка | Постоянная: правила придётся чинить |

**Вердикт: РЕКОМЕНДУЕМ как Фазу 2**, строго с моделью «черновик → подтверждение».
Как единственный источник данных — не годится, как дополнение к выписке — отличная вещь.

## 8. Способ 6. Чеки: OCR, QR кассового чека и ФНС

Здесь три разных по сути механики. Общее у них — они дают не «факт траты», а **детализацию**.

### 8.1. Ручной ввод по чеку + OCR фото

- Пользователь фотографирует чек, приложение распознаёт итоговую сумму и дату, подставляет в
  форму, пользователь правит.
- Технически: CameraX + OCR. Локальный OCR — это **новая тяжёлая зависимость** (ML Kit Text
  Recognition или аналог), плюс модель в APK. Облачный OCR — данные уходят наружу, что
  противоречит §14.
- Надёжность распознавания смятых термочеков — средняя. Итоговую сумму находить проще
  (ключевые слова «ИТОГ», «К ОПЛАТЕ»), позиции — сложно.
- **Оценка: 3–5 дней + зависимость. Вердикт: УСЛОВНО**, приятная мелочь, но низкий приоритет.

### 8.2. QR-код кассового чека и данные ФНС

Это более интересный путь, потому что он **не требует OCR**: на каждом фискальном чеке в РФ
печатается QR-код, содержащий структурированные реквизиты — дату/время, сумму, фискальный
признак и номера, идентифицирующие чек в системе ОФД/ФНС.

- **Что можно сделать локально, без сети:** отсканировать QR, распарсить строку реквизитов и
  сразу получить **точные дату, время и сумму**. Это уже полезно: быстрый ввод траты без
  ручного набора суммы. **Никакой сети и никаких аккаунтов не нужно.**
- **Что требует сети:** получить **состав покупки по позициям** (что именно куплено, по каким
  ценам). Сами реквизиты из QR состав не содержат — его надо запрашивать у сервиса, который
  хранит фискальные данные (ФНС / ОФД). Исторически такая проверка чеков доступна через
  сервисы и мобильное приложение ФНС «Проверка чека»; для программного доступа обычно нужна
  авторизация (например, регистрация в приложении ФНС по номеру телефона), и
  **официальность/стабильность программного интерфейса для сторонних приложений —
  [требует проверки]**. Никаких эндпоинтов здесь намеренно не приводится.
- **Ограничения:**
  - Работает только для **фискальных кассовых чеков** — то есть офлайн-покупки в рознице.
    Онлайн-оплаты, переводы, ЖКХ, такси-подписки часто останутся без чека.
  - Требует, чтобы пользователь **не выбросил чек** и отсканировал его — это ручное действие.
  - Данные позиций уходят через сеть → нарушается принцип §14, если делать это по умолчанию.
    Значит — только по явному действию пользователя, с предупреждением.
  - Названия позиций в чеках зашумлены (`МОЛОКО ПРОСТОКВ.3.2% 930МЛ`), для автокатегоризации
    по позициям потребуется отдельный словарь.
- **Ценность.** Уникальная фича: разложить один поход в супермаркет на «продукты / бытовая
  химия / алкоголь». Ни выписка, ни уведомление такого не дают. Но это **отдельная функция
  «детализация покупки»**, а не источник трат, и она требует расширения модели данных
  (позиции чека — это подтаблица к трате).
- **Оценка:** сканер QR + разбор реквизитов + быстрый ввод — **2–3 дня** (нужна библиотека
  сканирования — новая зависимость). Получение состава чека по сети — **+4–7 дней** и
  открытый вопрос по легальности/стабильности доступа.

**Вердикт: УСЛОВНО, отдельным треком.** Часть «QR → сумма и дата локально» — привлекательная,
дешёвая и безопасная; её можно сделать раньше, чем детализацию по сети. Часть «состав
покупки» — только после проверки актуального статуса доступа.

## 10. Рекомендуемая поэтапная стратегия

### Фаза 1. Импорт файла выписки

**Что даёт пользователю.** Возможность за одну минуту залить историю трат за несколько
месяцев вместо ручного ввода. Это снимает главный барьер входа в любое приложение учёта:
«я начал вести, забросил через три дня». Плюс регулярный сценарий «раз в месяц выгрузил
выписку — импортировал».

**Объём работ.**
- Приём файла (SAF + `ACTION_SEND`), определение формата/кодировки/диалекта.
- Парсер CSV + профили Т-Банка и Сбербанка + режим «ручной маппинг колонок» для остальных
  банков (это важно: он делает фичу универсальной без поддержки каждого банка).
- Нормализация сумм/дат, определение переводов между своими счетами.
- Автокатегоризация v1 (по MCC + словарь мерчантов, §12).
- Дедупликация (§13).
- Экран предпросмотра, импорт батчем, «Отменить импорт».
- Миграция БД 1 → 2 (§11).
- Тесты парсера на реальных (обезличенных) выписках.

**Итого: ~1.5–2 недели** с UI и тестами. XLSX — отдельной итерацией.

**Риски.**
- *Новые зависимости* для XLSX/PDF — противоречит текущему правилу «никаких новых
  зависимостей», требует явного согласования.
- *Формат выписок меняется* → снижаем риск режимом ручного маппинга колонок.
- *Пользователь не найдёт, где скачать выписку* → нужна короткая инструкция в приложении
  под каждый поддерживаемый банк.

### Фаза 2. Парсер уведомлений с подтверждением

**Что даёт пользователю.** Траты появляются в приложении сами, в момент покупки. Вечером
пользователь открывает «Требует подтверждения», за 20 секунд назначает категории и всё.
Это превращает приложение из «дневника, который надо вести» в «ленту, которую надо
разбирать» — принципиально другой уровень удержания.

**Объём работ.**
- `NotificationListenerService` + онбординг с переходом в системные настройки.
- Движок правил (чистая функция) + хранилище `parser_rules` + базовый набор в assets.
- Экран «Требует подтверждения»: карточки с суммой, мерчантом, предложенной категорией,
  свайпами «подтвердить/удалить».
- Дедупликация против импортов (§13).
- Обучение автокатегоризации на подтверждениях (§12).
- Тесты на корпусе текстов уведомлений.
- Раскрытие в политике конфиденциальности и Data Safety.

**Итого: ~1.5–2 недели.**

**Риски.**
- *Правила ломаются при изменении текста пуша* → `rawText` + переразбор + видимая метрика
  «сколько уведомлений не распознано».
- *Ревью Google Play* → готовим текст раскрытия заранее; функция не должна быть
  обязательной для работы приложения.
- *Батарея и производительность* → никакой тяжёлой работы в `onNotificationPosted`.
- *Ложные срабатывания* → всё через `PENDING`, ничего не пишется молча.

### Фаза 3. API / агрегаторы

**Что даёт пользователю.** Полностью автоматический, полный и точный учёт без единого
действия.

**Объём работ.** Не оценивается в днях разработки, потому что основная работа —
не разработка: юрлицо, договор, комплаенс, серверная инфраструктура, обработка ПДн,
подписочная модель для оплаты доступа.

**Риски.** Полная смена природы продукта: из офлайн-приложения он становится сервисом с
серверами и ответственностью за чужие финансовые данные.

**Условие входа в фазу:** появление доступной программы открытых API для приложений
персональных финансов **или** приемлемого по цене и условиям агрегатора. **Действие
сейчас — только мониторинг статуса.**

### Что делать в промежутке

Дешёвые улучшения, повышающие ценность любой из фаз:
- Ручной маппинг колонок при импорте (делает Фазу 1 универсальной).
- Словарь мерчант → категория, пополняемый пользователем.
- QR-сканер чека для быстрого ввода суммы и даты (§8.2, локальная часть).

## 11. Влияние на модель данных

Ниже — предложение изменений. Всё это **миграция `AppDatabase` версии 1 → 2** (сейчас
`version = 1` и миграций нет; `exportSchema = true` уже включён, схема есть — это упрощает
написание и тестирование миграции через `MigrationTestHelper` из `room-testing`).

### 11.1. Изменения в `expenses` (`ExpenseEntity`)

Добавляемые поля — **все nullable либо с DEFAULT**, чтобы миграция была простым `ALTER TABLE`
без пересоздания таблицы и без потери данных:

| Поле | Тип | Назначение | Значение для существующих строк |
|---|---|---|---|
| `source` | `TEXT NOT NULL DEFAULT 'MANUAL'` | `MANUAL` / `IMPORT` / `NOTIFICATION` / `SMS` / `RECEIPT` / `API` | `MANUAL` |
| `status` | `TEXT NOT NULL DEFAULT 'CONFIRMED'` | `CONFIRMED` / `PENDING` / `UNPARSED` / `REJECTED` | `CONFIRMED` |
| `externalId` | `TEXT NULL` | Идентификатор операции из источника (ID банка, или наш детерминированный хеш). Уникальный индекс с учётом источника | `NULL` |
| `accountId` | `INTEGER NULL` | FK на `accounts` | `NULL` |
| `bank` | `TEXT NULL` | Код банка-источника (`TBANK`, `SBER`, ...), денормализовано для правил и фильтров | `NULL` |
| `merchantRaw` | `TEXT NULL` | Сырое имя мерчанта/получателя до нормализации — основа автокатегоризации | `NULL` |
| `mcc` | `INTEGER NULL` | MCC-код (только из выписки) | `NULL` |
| `operationTimeMillis` | `INTEGER NULL` | Точное время операции. **`epochDay` остаётся ведущим полем даты** — не ломаем существующие запросы и статистику; время нужно только для дедупликации и сортировки внутри дня | `NULL` |
| `rawText` | `TEXT NULL` | Исходная строка выписки / текст уведомления. Нужен для переразбора и разбора инцидентов | `NULL` |
| `importBatchId` | `INTEGER NULL` | FK на `import_batches`, для отката импорта | `NULL` |
| `parserRuleId` | `INTEGER NULL` | Каким правилом распознано (FK на `parser_rules`) | `NULL` |

Индексы, которые понадобятся дополнительно к существующим:

- `UNIQUE (source, externalId)` — частичный/с учётом `NULL` (в SQLite `NULL` не конфликтует
  сам с собой, так что уникальный индекс по двум колонкам корректно пропустит ручные записи).
- `INDEX (status)` — экран «Требует подтверждения» дёргается часто.
- `INDEX (importBatchId)` — откат импорта.
- `INDEX (accountId)`.
- `INDEX (epochDay, amountMinor)` — окно дедупликации (§13).

**Важно для совместимости:** все существующие запросы `ExpenseDao` считают, что в `expenses`
лежат только реальные траты. После введения `status` **все выборки для списка, статистики и
экспорта обязаны фильтровать `status = 'CONFIRMED'`**, иначе черновики попадут в графики.
Это ключевой пункт при реализации — его легко забыть.

Альтернатива, которую стоит рассмотреть: держать неподтверждённые операции **в отдельной
таблице `pending_operations`** и переносить в `expenses` только при подтверждении. Плюс —
нулевой риск «протечки» черновиков в статистику и никаких изменений в существующих запросах.
Минус — дублирование полей и логики. **Рекомендация: отдельная таблица `pending_operations`**
— она безопаснее для уже работающего кода, а `status` в `expenses` оставить только как
метку происхождения (`CONFIRMED` всегда).

### 11.4. Скетч миграции 1 → 2

Иллюстративно (точный код пишется при реализации, здесь важна форма — только `ALTER TABLE`
и `CREATE`, без пересоздания `expenses`):

```sql
ALTER TABLE expenses ADD COLUMN source TEXT NOT NULL DEFAULT 'MANUAL';
ALTER TABLE expenses ADD COLUMN externalId TEXT;
ALTER TABLE expenses ADD COLUMN accountId INTEGER;
ALTER TABLE expenses ADD COLUMN bank TEXT;
ALTER TABLE expenses ADD COLUMN merchantRaw TEXT;
ALTER TABLE expenses ADD COLUMN mcc INTEGER;
ALTER TABLE expenses ADD COLUMN operationTimeMillis INTEGER;
ALTER TABLE expenses ADD COLUMN rawText TEXT;
ALTER TABLE expenses ADD COLUMN importBatchId INTEGER;

CREATE TABLE accounts (...);
CREATE TABLE import_batches (...);
CREATE TABLE parser_rules (...);
CREATE TABLE merchant_rules (...);
CREATE TABLE pending_operations (...);

CREATE UNIQUE INDEX index_expenses_source_externalId ON expenses (source, externalId);
CREATE INDEX index_expenses_importBatchId ON expenses (importBatchId);
CREATE INDEX index_expenses_accountId ON expenses (accountId);
CREATE INDEX index_expenses_epochDay_amountMinor ON expenses (epochDay, amountMinor);
```

Замечания по реализации миграции:

- SQLite **не позволяет добавить колонку с FK через `ALTER TABLE`** так, чтобы Room увидел
  внешний ключ. Для `accountId` / `importBatchId` либо обходимся индексом без FK-констрейнта
  (и целостность держим в коде), либо идём на пересоздание таблицы `expenses` с копированием
  — что дороже и рискованнее. **Рекомендация: без FK на эти два поля.**
- В `AppDatabase` уже включён `PRAGMA foreign_keys = ON` в `onOpen` — при пересоздании таблиц
  в миграции это нужно учитывать (Room оборачивает миграции в транзакцию).
- Миграцию обязательно покрыть тестом `MigrationTestHelper` (зависимость `room-testing`
  уже доступна) — проверить, что данные v1 выживают.
- `fallbackToDestructiveMigration()` **не использовать** — это удаление всех трат
  пользователя.

## 12. Автокатегоризация

Цель: чтобы импортированная или распознанная операция сразу приходила с правильной
категорией из существующих 17, и пользователю оставалось только пролистать и подтвердить.

### 12.1. Сигналы, по убыванию надёжности

1. **Пользовательское правило** (`merchant_rules.isUserDefined = 1`) — абсолютный приоритет.
   Если пользователь один раз сказал «ПЯТЁРОЧКА → Продукты/Супермаркет», больше не спрашиваем.
2. **История собственных подтверждений.** Тот же нормализованный мерчант уже встречался и был
   отнесён к категории X в ≥ N случаях (и без противоречий) → предлагаем X. Фактически это
   автоматическая генерация правил.
3. **MCC-код** (есть только в выписке). Стабильный, языконезависимый сигнал: например,
   продуктовые магазины, АЗС, аптеки, такси имеют устойчивые MCC-группы. Встроенная таблица
   `MCC-группа → категория` покрывает большую часть трат по карте одним махом.
4. **Встроенный словарь мерчантов** — список известных сетей → категория. Небольшой,
   но покрывает частотные кейсы.
5. **Категория банка из выписки** — маппится на нашу таксономию таблицей соответствий.
   Слабый сигнал: банк ошибается и его категории не совпадают с нашими.
6. **Ключевые слова в назначении платежа** — самый слабый сигнал, много ложных срабатываний.
   Использовать только как последний резерв.

### 12.2. Нормализация имени мерчанта

Без неё правила не работают. Из `merchantRaw` вида
`RUS MOSCOW PYATEROCHKA 5643 / ООО "АГРОТОРГ"` нужно получить стабильный ключ:

- верхний регистр, схлопывание пробелов;
- удаление кодов стран/городов, номеров точек, длинных числовых хвостов;
- удаление организационно-правовых форм (`ООО`, `АО`, `ИП`, `LLC`);
- транслитерация латиница ↔ кириллица для сопоставления (`PYATEROCHKA` ↔ `ПЯТЁРОЧКА`),
  включая нормализацию `ё → е`;
- итог — короткий ключ, по которому и матчим.

Нормализатор — чистая функция, покрывается юнит-тестами.

### 12.3. Обучение на подтверждениях

Простая и объяснимая схема, без ML:

- При подтверждении операции с категорией, отличной от предложенной, записываем «голос» за
  пару (нормализованный мерчант → категория).
- Как только по мерчанту накопилось ≥ 2 непротиворечивых голоса — **автоматически создаём
  правило** в `merchant_rules` (`isUserDefined = 1`) и показываем ненавязчивую плашку
  «Запомнили: ПЯТЁРОЧКА → Продукты. Изменить».
- Если пользователь позже меняет категорию для того же мерчанта — правило перезаписывается.
- Экран «Правила категоризации» в настройках: список, поиск, удаление, ручное добавление.

Это даёт эффект обучения при полной предсказуемости и без «магии», которую невозможно
отладить.

### 12.4. Уверенность и что с ней делать

У каждого предложения есть источник сигнала, а значит — уровень уверенности:

| Уверенность | Источник | Поведение |
|---|---|---|
| Высокая | Пользовательское правило, MCC точного попадания | Подставить категорию, не выделять |
| Средняя | Встроенный словарь, категория банка | Подставить, но пометить точкой «предположение» |
| Низкая / нет | Ничего не совпало | Категория **не подставляется**; операция попадает в «Требует подтверждения» с фокусом на выборе категории |

**Никогда не подставлять «Прочее» молча** — это худший исход: пользователь не заметит, и
статистика тихо испортится. Лучше честно попросить выбрать.

## 13. Дедупликация

Проблема реальна: одна покупка легко приходит трижды — пуш в момент оплаты, строка в
выписке за месяц, и ещё раз при повторном импорте пересекающегося периода.

### 13.1. Уровни защиты, по убыванию надёжности

**Уровень 1 — `externalId` (точное совпадение).**
Если источник даёт идентификатор операции — используем его напрямую. Уникальный индекс
`(source, externalId)` физически не даст вставить дубль.

Если идентификатора нет (обычный случай для CSV), строим **детерминированный синтетический
ключ**: хеш от `(bank, accountMask, дата, время, сумма, нормализованный мерчант)`. Тогда
повторный импорт того же файла даёт те же ключи → дубли отсекаются автоматически. Важно,
чтобы функция ключа была **стабильной между версиями приложения** — при её изменении надо
уметь пересчитать ключи для существующих строк.

**Уровень 2 — окно нечёткого совпадения (для пуш ↔ выписка).**
Здесь `externalId` не совпадёт никогда: у пуша его нет, а время отличается. Правило:

- **сумма совпадает точно** (в копейках) — обязательное условие, никаких допусков;
- **счёт совпадает** (по `accountId` или по последним 4 цифрам карты; если счёт неизвестен —
  условие ослабляется, но растёт риск ложного слияния);
- **время в окне ±72 часа** — широкое окно нужно потому, что дата операции по карте и дата
  списания расходятся; сузить до ±24 часов, если оба источника дают точное время;
- **мерчанты похожи** — нормализованные имена совпадают или одно содержит другое.
  Если мерчанта нет ни у одной стороны — сигнал не учитывается.

Совпало по сумме + счёту + окну → **кандидат в дубли**.

**Уровень 3 — приоритет источников при слиянии.**
Если дубль подтверждён, **выигрывает более полная запись**:
`IMPORT (выписка) > RECEIPT > NOTIFICATION > SMS > MANUAL`.
Практически: при импорте выписки найденная запись из уведомления **не удаляется, а
обогащается** — ей проставляются `mcc`, `externalId`, точная дата, полное назначение,
`source` меняется на `IMPORT`. При этом **сохраняется категория, которую выбрал пользователь**
— его выбор всегда важнее автокатегоризации.

**Уровень 4 — ручное слияние.**
Автоматика не должна решать в спорных случаях. Нужен UI:
- в предпросмотре импорта дубли-кандидаты подсвечены и **по умолчанию сняты** с импорта,
  с возможностью включить обратно;
- в списке трат — действие «Объединить с...» для двух выбранных операций;
- «сомнительные» пары (совпала сумма, но мерчанты разные) — не сливать автоматически,
  показать пользователю.

### 13.2. Ловушки

- **Две одинаковые реальные покупки подряд.** Два кофе по 200 ₽ с разницей в 3 минуты — это
  не дубль. Именно поэтому автослияние по «сумма + окно» **без совпадения мерчанта и без
  разных источников** делать нельзя. Правило: **сливать только записи из разных источников**;
  две записи из одного источника — почти наверняка две разные покупки.
- **Частичная отмена / доплата** на ту же сумму.
- **Регулярные платежи** (подписка 299 ₽ каждый месяц) — разница в датах велика, окно их
  не заденет.

## 14. Приватность и безопасность

Это не формальный раздел: приватность — фактически главное конкурентное преимущество
локального приложения учёта трат.

### 14.1. Базовый принцип

> **Данные не покидают устройство.** Ни в каком виде, ни в какую аналитику, ни в какие
> облака — пока пользователь сам явно этого не попросил (экспорт, поделиться файлом).

Практические следствия:

- Приложение **не имеет разрешения `INTERNET`** — и это надо сохранить как можно дольше.
  Отсутствие сетевого разрешения в манифесте — самое сильное и проверяемое обещание
  приватности, которое можно дать.
- Любая фича из §4, §5, §8.2 **ломает это обещание** и требует отдельного, осознанного
  решения — с явным экраном согласия и возможностью не включать.
- Никакой сторонней аналитики, крашлитики и рекламных SDK в сборке.

### 14.2. Шифрование БД

Сейчас БД `spendtracker.db` лежит в приватном хранилище приложения незашифрованной. Для
обычного устройства этого достаточно (sandbox + FBE), но:

- на **рутованном** устройстве файл читается любым приложением с root;
- при **ADB-бэкапе** и некоторых сценариях восстановления данные могут утечь.

С появлением банковских данных (маски карт, полные назначения платежей, полная история
покупок) планка повышается. Варианты:

- **SQLCipher** (`net.zetetic:android-database-sqlcipher` + `androidx.sqlite`) — прозрачное
  шифрование всей БД. **Это новая зависимость** и увеличение размера APK; ключ хранится в
  Android Keystore, при желании — с привязкой к биометрии (пересекается с задачей
  «биометрический замок» в `roadmap.md`).
  Минусы: усложняется отладка, миграция существующей незашифрованной БД требует отдельного
  аккуратного шага (перенос данных в новый зашифрованный файл), потеря ключа = потеря данных.
- **Компромисс:** шифровать не всю БД, а только чувствительные поля (`rawText`, `merchantRaw`,
  маски карт). Дешевле, но защищает частично.

**Рекомендация:** SQLCipher вводить **вместе с Фазой 1** — то есть в тот же момент, когда в
базе впервые появляются банковские данные. Позже мигрировать будет сложнее.
Обязательно предусмотреть путь миграции и предупредить, что при включении привязки к
биометрии сброс биометрии на устройстве может сделать ключ недоступным.

### 14.3. Что нельзя логировать

Категорический запрет на попадание в `Logcat` (и в любой файл логов, если он появится):

- полный текст банковских уведомлений и SMS;
- `rawText` строк выписки;
- номера карт и счетов в любом виде, включая маски;
- ФИО, телефоны и имена получателей переводов;
- суммы и остатки по счёту;
- содержимое импортируемого файла и его полный путь.

Правила:
- В release-сборке логирование **отключено полностью** (`Timber`-подобная обёртка или
  просто `if (BuildConfig.DEBUG)`); проверить, что ProGuard/R8 вырезает вызовы логгера.
- В debug — логировать **только агрегаты и метки**: «распознано правилом #12», «строк 342,
  импортировано 298». Не значения.
- В сообщениях об ошибках парсинга, показываемых пользователю, — номер строки, а не её
  содержимое (содержимое можно показать в UI, но не писать в лог).
- **Обработчик крашей**, если он когда-нибудь появится, не должен собирать содержимое БД
  и значения переменных.

### 14.4. Экспорт

Экспорт (`CsvExporter`, `JsonExporter`, `AnalysisBundle`) — легальный и намеренный способ
вынести данные с устройства, но он же — главный канал утечки:

- Файлы пишутся в `context.cacheDir/exports/` и отдаются через FileProvider — правильно.
  Нужно добавить **очистку старых экспортов** при запуске (сейчас файлы копятся в кэше).
- В экспорт **не включать** `rawText`, маски карт и полные назначения платежей по умолчанию.
  Это особенно важно для `AnalysisBundle` — отчёт для ИИ пользователь отправляет во внешний
  сервис. Там должны быть только агрегаты и обезличенные категории. Если добавлять мерчантов
  — только по явному переключателю с предупреждением.
- Предупредить пользователя перед «Поделиться»: «файл содержит вашу историю трат».
- В `JsonExporter` при появлении новых полей — осознанно решить по каждому, попадает ли оно
  в выгрузку.

### 14.5. Разрешения и раскрытие

- Не запрашивать ни одного разрешения «на будущее». Доступ к уведомлениям — только при
  включении соответствующей функции, с экраном-объяснением до перехода в настройки.
- Заполнить **Data Safety** в Play Console честно: какие данные собираются, что они не
  покидают устройство, что не передаются третьим лицам.
- Иметь короткую и настоящую политику конфиденциальности.

## 15. Что мы НЕ будем делать и почему

### 15.1. Спрашивать логин и пароль от интернет-банка

**Категорически неприемлемо.** Модель, где приложение просит учётные данные от банка и затем
«ходит» в интернет-банк под пользователем (скрейпинг личного кабинета), отвергается
полностью, даже если технически она сработает и даже если пользователь сам попросит.

Причины:

1. **Прямое нарушение договора пользователя с банком.** Правила дистанционного банковского
   обслуживания практически всегда запрещают передачу учётных данных третьим лицам.
2. **Пользователь лишается защиты при мошенничестве.** Передав кому-то доступ, он нарушил
   условия — и банк на законных основаниях откажет в возмещении при списании средств.
   То есть мы своим приложением создаём ему финансовый риск. Это неприемлемо независимо от
   нашей аккуратности.
3. **Мы становимся хранителем банковских учётных данных.** Даже «только на устройстве» —
   это ответственность, которую нельзя брать: одна уязвимость = скомпрометированные счета.
4. **Обход двухфакторной аутентификации.** Чтобы такая схема работала автоматически,
   приложению нужно перехватывать одноразовые коды — то есть ровно то поведение, которое
   отличает банковский троян от легального софта. Мы не будем строить продукт, чей код
   неотличим от вредоноса.
5. **Технически это мина.** Любой редизайн или новая антибот-защита ломает интеграцию;
   поведение выглядит для банка подозрительно и приводит к блокировке аккаунта пользователя.

**Это правило распространяется и на посредников:** если агрегатор из §5 под капотом работает
по такой схеме, он нам не подходит.

### 15.2. Использовать недокументированные внутренние API банковских приложений

Реверс мобильного приложения банка, подделка его запросов, извлечение токенов из чужого
приложения — нарушение условий использования, вероятная блокировка пользователя и
нестабильность по определению. Не делаем.

### 15.3. Читать содержимое чужих приложений через Accessibility Service

Технически позволяет «увидеть» экран банковского приложения. На практике: Google Play крайне
жёстко ограничивает использование Accessibility не по назначению (это функция доступности для
людей с ограниченными возможностями), а сам приём — классика банковских троянов. Не делаем.

### 15.4. Отправлять данные трат во внешние сервисы без явного действия пользователя

Никакой фоновой синхронизации «для улучшения категоризации», никакой отправки мерчантов на
сервер для распознавания, никакой облачной аналитики. Автокатегоризация — только локальная
(§12). Единственный внешний обмен — тот, который пользователь инициировал сам (экспорт,
и потенциально §8.2 с явным согласием).

### 15.5. Молча создавать траты

Ни одна операция из уведомления/SMS не должна попасть в статистику без подтверждения
пользователя (по умолчанию). Иначе цифры «куда уходят деньги» перестают быть надёжными,
а пользователь теряет доверие к приложению — и это дороже любой автоматизации.

## 16. Открытые вопросы

Их нужно закрыть до старта реализации:

1. **Новые Gradle-зависимости.** Текущее правило `CONTRACT.md` — «никаких новых
   зависимостей». Импорт XLSX, PDF, OCR, QR-сканер и SQLCipher его нарушают. Нужно решение:
   что разрешаем и в какой момент. Минимальная Фаза 1 (CSV) реализуема **без единой новой
   зависимости** — это аргумент начать именно с неё.
2. **Собрать реальные обезличенные выписки** Т-Банка и Сбербанка (CSV и PDF) как тестовый
   корпус. Без них любые оценки по §3.3–3.4 остаются предположениями.
3. **Собрать корпус текстов push-уведомлений** этих банков — без него нельзя написать и
   протестировать правила §7.
4. **Решить: `status` в `expenses` или отдельная таблица `pending_operations`** (§11.1).
   Рекомендация в документе — отдельная таблица, но это надо утвердить до миграции.
5. **Проверить актуальный статус** программ открытых API (§4) и политики Google Play по
   SMS и доступу к уведомлениям (§6.2, §7.4) — непосредственно перед реализацией
   соответствующей фазы.
6. **Мультивалютность.** Покупки за рубежом в выписке есть уже сейчас. Решить: игнорировать
   (импортировать сумму в валюте счёта) или ждать полноценной поддержки валют из
   `roadmap.md`. Рекомендация — первое.
7. **Доходы.** Выписка содержит и поступления. В v1 модели их некуда положить. Решить:
   пропускать (рекомендация для Фазы 1) или сначала сделать задачу «доходы и баланс».
